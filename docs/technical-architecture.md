# 短剧互动入口技术文档

## 项目概述

本项目是一个面向展示与验证的网页原型，目标是把“短剧链接接入”与“看完后立即入戏”的互动体验串成一个完整闭环。

用户当前看到的流程是：

1. 打开页面
2. 粘贴一个短剧链接
3. 进入约 1 秒的 `Thinking...` 处理中转场
4. 播放短剧视频
5. 视频播放结束后上滑入戏
6. 进入五幕式互动剧情

当前版本的重点不是实现真实的全自动视频解析，而是先验证一种产品形态：

- 链接接入是否自然
- 观看到互动的切换是否顺滑
- 短剧结束后的“继续玩下去”是否有吸引力

从定位上看，它更接近一个“AI 短剧互动入口原型”，而不是一个完整的视频理解平台。

## 产品设计

### 1. 设计目标

这个产品不是聊天工具，也不是传统文字跑团面板，而是一个更接近 AIGalgame / 互动短剧的体验。

设计上优先保证三件事：

- 用户第一眼先理解入口，而不是先被复杂系统界面打断
- 视频与互动之间有明确的情绪承接
- 入戏以后不是自由散聊，而是沿着主剧情推进的可玩结构

### 2. 用户路径

当前版本采用四段式路径：

- `链接页`
  用户输入短剧链接，完成接入动作
- `thinking 过场`
  用极短的处理中转场把用户快速推进到故事里
- `视频页`
  播放短剧内容，并在结束时给出上滑进入互动的动作提示
- `互动页`
  用户进入五幕式剧情，并通过选项或自由行动继续参与故事

### 3. 产品叙事策略

虽然当前所有链接都会走向同一条视频，但产品叙事上仍然保留“链接接入 -> 系统理解 -> 打开故事”的完整表层体验。

这样做有两个好处：

- 在不引入真实解析复杂度的情况下，先完成产品感验证
- 后续如果接入真实能力，不需要推翻前端交互结构

## 技术架构

### 1. 前端结构

当前项目是一个纯静态前端应用，主要由以下文件构成：

- `index.html`
  页面骨架，定义 4 个主面板
- `styles.css`
  负责首屏、loading、视频页和互动页的视觉样式
- `app.js`
  负责状态流、面板切换、视频控制、五幕剧情推进和本地数值反馈
- `assets/drama-demo-web.mp4`
  当前固定播放的视频资源

页面内部划分为 4 个主面板：

- `#intakePanel`
  链接输入页
- `#loadingPanel`
  thinking / 剧情接入的中转页
- `#videoPanel`
  视频播放页
- `#gamePanel`
  五幕互动剧情页

面板切换由 `app.js` 中的 `setPanel(panel)` 统一控制。

### 2. 状态管理

前端核心状态集中在 `state` 对象中，主要包括：

- `sourceUrl`
  当前接入的短剧链接
- `sourceAccepted`
  当前链接是否已经被系统接收
- `chapterIndex`
  当前五幕剧情的进行位置
- `selectedTools`
  用户当前选择的道具
- `dialogueStep`
  单幕内的对话推进位置
- `scores`
  用户的威望、线索、危险等数值

### 3. AI 能力使用方式

这是当前技术架构里最重要的一部分。

#### 当前版本的 AI 使用方式

当前版本**没有真正调用外部 AI 服务**，但保留了完整的 AI 产品交互壳层。

具体来说：

- 用户输入任意链接
- 前端进入 `Thinking...` 过场
- 过场只保留极短的“故事接入”反馈
- 处理结束后进入固定视频
- 视频结束后进入硬编码的五幕剧情结构

也就是说，当前 AI 的实现方式是：

- 在交互层伪装成“系统理解内容”
- 在数据层仍然使用本地固定视频和本地固定剧情

这种方式的意义不是欺骗，而是为了在产品原型阶段先验证体验路径，再决定真实能力是否值得接入。

#### 当前 AI 壳层的替换点

如果后续要接入真实 AI，推荐替换点放在 `acceptSource()` 之后，也就是链接提交完成之后、视频打开之前。

理想流程应为：

1. 用户提交链接
2. 前端调用后端任务
3. 后端完成视频获取 / 结构分析 / 剧情抽取
4. 后端返回结构化结果
5. 前端用真实结果替换当前本地固定资源

推荐的后端返回结构可以是：

```json
{
  "videoUrl": "https://...",
  "title": "海上旧约",
  "summary": "短剧剧情摘要",
  "acts": [
    {
      "title": "宴席逼问",
      "speaker": "大伯",
      "text": "你怎么在这片海上活下去？"
    }
  ]
}
```

#### AI 能力未来可拆分的模块

如果继续往前走，AI 能力建议按 4 层拆分：

- `链接解析层`
  获取视频真实地址、封面、标题、基础元数据
- `内容理解层`
  对视频做剧情摘要、角色识别、关键冲突抽取
- `结构生成层`
  把视频内容转成适合互动的五幕或关卡树结构
- `互动生成层`
  根据用户行动动态生成分支反馈、旁白和剧情推进

当前项目只保留了这四层的“产品接口形态”，尚未接入真实实现。

## 核心实现

### 1. 链接接入与 thinking

用户提交链接后触发 `acceptSource(rawValue)`。

当前逻辑会：

1. 校验输入是否为空
2. 把链接写入 `state.sourceUrl`
3. 把链接同步到浏览器 URL query 中
4. 调用 `runSourceThinking()`

`runSourceThinking()` 内部复用了 `runLoadingSequence()`，现在采用一段极短过场：

- `正在接入故事...`

这一段停留约 1 秒，重点不是表现复杂推理，而是快速把用户推入视频与剧情。

### 2. 视频播放与入戏

thinking 结束后调用 `playVideo()`。

这个函数会：

- 重置视频播放状态
- 切换到 `videoPanel`
- 显示左上角的链接信息卡
- 自动尝试播放视频

视频播放结束后由 `finishVideo()` 触发，页面会显示“上滑入戏”。

只有在 `sourceAccepted = true` 且视频结束后，用户才可以进入互动剧情。

### 3. 五幕剧情结构

互动层由 `chapters` 数组驱动，每一幕包含：

- `title`
- `speaker`
- `text`
- `prose`
- `dialogues`
- `choices`
- `backdrop`

这意味着互动内容并不是零散拼接的聊天消息，而是一个结构化、可控的剧情序列。

当前交互也已经从“逐句点击推进对话”转成“场景处境 + 即时行动”的沉浸式节奏：

- 进入每一幕后直接看到当前处境
- 直接给出行动选项
- 选择后立即结算结果并推进下一幕

### 4. 选项与自由行动

每一幕提供两种参与方式：

- 点击预设选项
- 输入自由行动

无论哪一种方式，最终都会转成统一的本地结果结算逻辑：

- 更新数值
- 输出反馈文字
- 自动推进到下一幕

### 5. 通用 loading 复用

`loadingPanel` 目前被复用在两个场景：

- 链接接入后的 thinking
- 视频结束后进入互动页前的短过场

这部分由 `runLoadingSequence({ title, steps, stepDuration })` 统一实现，减少了重复的状态控制代码。

## 作品亮点

### 1. 入口叙事完整

虽然当前底层是固定视频与固定剧情，但表层体验已经具备“贴链接 -> 系统理解 -> 打开故事 -> 入戏互动”的完整叙事闭环。

### 2. 视频与互动衔接明确

不是把视频和互动拆成两个孤立页面，而是让视频结尾自然成为互动剧情的入口，这一点比纯聊天式体验更有产品感。

### 3. 技术结构适合后续替换真实能力

当前实现虽然是原型，但入口层、视频层、剧情层已经做了基本解耦。以后若接入真实 AI，不需要整站重写，只需要替换链接提交后的处理部分。

### 4. 剧情呈现方式更接近可玩的短剧

这不是一个泛用聊天界面，也不是后台工具面板，而是一个更接近互动视觉小说的轻量原型，方向上更适合做内容型展示。

## 已知局限与后续规划

### 已知局限

- 当前不会真实解析外部链接
- 当前不会真实切换到外部视频资源
- thinking 过场是产品层模拟，不是模型实时推理
- 五幕剧情仍然是前端硬编码
- 数值系统只影响本地反馈，不与真正的剧情生成联动
- 没有接入用户存档、账号系统或后端同步

### 后续规划

建议下一步按下面顺序推进：

1. 继续优化链接页、thinking 页和视频页的产品质感
2. 把五幕剧情升级成更明确的关卡树和分支成长结构
3. 在不破坏现有体验路径的前提下，逐步把“假接入”替换成“真解析”
4. 最后再评估是否需要接入真实的动态剧情生成能力

这样做的原因是：

- 先验证产品形态是否成立
- 再决定是否为真实 AI 能力支付复杂度成本
- 避免过早进入高成本工程实现，却没有把体验先做顺
